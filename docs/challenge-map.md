# 挑战副本：续玩、消耗、恢复、奖励与扫荡

实现位于 `handlers/challenge_map.py`。副本要求读取客户端
`fzjh_lua/assets/res/script/challengeMap/mapInfo.lua` 的 161 条配置，
包括等级、标记、门票可选项、轶闻值消耗、开放时间及次数限制。

## 接口与状态

以下接口均要求有效的 `userid` 请求头，路径前缀为 `/api/v5/`。

| 方法 | 接口 | 行为 |
| --- | --- | --- |
| GET | `challengemap_unfinished` | `data.status`：0 无副本；1 可续玩；2 已过期、须离开 |
| POST | `challengemap_enter` | `{map_id}` 检查资格，保存 5 分钟有效的进入预览，不扣费 |
| POST | `challengemap_confirm_consume` | `{map_id, consume_map:[{id,num}]}` 校验门票、扣费并创建会话 |
| GET | `reenter_challengemap` | 返回 `data.challengemap.map_id` 等会话信息；不再次扣费或延期 |
| POST | `challengemap_leave` | `{type:1\|2\|3}` 主动离开、失败离开、重连放弃；清除会话，不退款 |
| GET | `get_user_anecdote` | 返回恢复后的 `number,max_number` |
| GET | `test_revert_anecdote` | 客户端已有的调试接口，补满轶闻值，不清除副本 |
| POST | `get_festivalmap_info` | `{groupId}` 返回按等级排列的 `dayTime,finalTime` 次数 |
| POST | `challengemap_is_customs` | `{map_id}` 检查扫荡资格，保存 5 分钟扫荡预览，不扣费 |
| POST | `challengemap_finish` | `{map_id,finish_type:1\|2}` 准备普通通关或扫荡结算，返回 `award_id` |
| POST | `challengemap_award` | `{map_id,finish_type,type:1\|2,award_list,currencyVersion?}` 领取已准备的奖励 |

进入流程为：预览 → 确认扣费 → 可续玩 → 离开。已有会话时不能新开副本；
过期会话返回状态 2，客户端须调用离开接口后重新预览。
例如 `tzfb0101` 要求等级 600、消耗 15 点轶闻值，不需要门票。

门票必须与每组配置中的某个选项严格匹配，数量由服务端配置决定，支持背包多堆叠扣除。
同一存续会话内重复、并发提交相同确认参数返回原确认结果，不重复扣费。
离开后须重新预览才能再次扣费；客户端协议不提供请求幂等键，因此不保证跨不同会话的
任意延迟旧请求去重。重试确认返回的是原支付余额，当前恢复余额应查询 `get_user_anecdote`。

## 持久化与 Mock 规则

账户 `currencies.anecdote` 是余额权威来源，首次缺失时才从角色存档迁移，
再缺失则初始化为上限。零余额不被当成未初始化，旧存档不会覆盖已有账户余额。
`anecdote_recovered_at` 保存恢复时间，`challenge_map` 保存待确认信息、会话和次数。
扣费同时更新角色存档中的轶闻值及门票；恢复时只更新账户余额。
正常保存、重启后可继续原会话，并按离线经过时间恢复余额。
账户状态和角色存档沿用现有存储机制，不是跨文件数据库事务，不承诺断电写入中途的原子性。

以下默认值是便于本地联调的 **Mock 规则，未验证为正式服规则**：

| 环境变量 | 默认值 | 含义 |
| --- | --- | --- |
| `MOCK_ANECDOTE_MAX` | 100 | 恢复上限；保留已有超上限余额 |
| `MOCK_ANECDOTE_RECOVER_SECONDS` | 600 | 每恢复 1 点所需秒数 |
| `MOCK_CHALLENGE_SESSION_SECONDS` | 86400 | 会话有效秒数，且不超过活动结束时间 |

恢复按请求触发结算，保留不足一周期的剩余时间；满值不积攒恢复时间，时钟回拨不增加余额。
次数在成功确认进入时增加，按北京时间零点换日，总次数不自动重置。
客户端活动配置中的历史时间窗仍生效，没有自动放开已经结束的节日活动。
修改环境变量后需重启 Mock 服务。调试补满接口仅用于本地 Mock，不应作为正式服接口使用。

## 奖励与扫荡

普通通关：已付费会话 → `finish(finish_type=1)` → `award(finish_type=1)`。
扫荡：`is_customs` → `finish(finish_type=2)` → `award(finish_type=2)`。
客户端扫荡不调用普通进入/确认扣费接口，也不上传门票选择；服务端按客户端顺序选择
背包中第一个足量的门票选项，在扫荡 `finish` 中复用进入扣费逻辑，仅扣一次并计一次次数。
执行时会重新检查等级、开放时间、次数、门票和轶闻值，不能依靠过期预览绕过限制。

当前采用保守 Mock 门槛：该账号正常通关并领取奖励后才解锁对应副本的扫荡。
仅支持配置了 `cleanId` 的副本（当前 18 个），没有配置的活动副本不会凭空生成扫荡奖励。
正常通关记录随账户保存，并通过登录信息中的 `challengeMapCompleted` 回传客户端。

奖励生成读取 `rewardScheme.lua`、`map/mapItemAttr/Rewards.lua`，支持嵌套策略、
权重随机、组合奖励及无奖励分支。当前挑战配置可达的 210 条叶子奖励都是固定数量的
物品、属性或称号；未来遇到未支持的计算类型会报错，不会直接执行 Lua 表达式或先扣扫荡费用。
普通通关使用 `awardId`，扫荡使用 `cleanId`；奖励箱本身就是配置物品，不提前展开箱内奖励。
服务器资源使用地图 `rsesources`。配置没有提供单独的扫荡资源数量，因此 Mock 普通与扫荡
沿用同一资源表，仅奖励策略不同；这不是已验证的正式服差异规则。

`finish` 将服务端随机结果保存在会话内，`award_list` 上传内容只作为兼容输入，不决定发放内容。
客户端也会随机计算一次奖励，但最终以服务端返回的 `award_list` 为准，两次随机结果可能不同。
`type=1` 直接发放；`type=2` 将物品存入邮驿的 `loc_items`，属性、称号和服务器资源仍直接发放。
背包是否足够沿用客户端的 `type` 判断，服务端没有额外重建背包容量规则。
资源沿用现有服务器上限（如 `zongheng=9999`），返回实际发放数量和上限提示。
服务端生成递增 `currencyVersion`，不采纳客户端任意增大的版本号。

成功领取后会清除活动会话并保存最近一次结算回执。重复 `finish`/`award` 不重抽奖励、
不多扣费用、不多发物品或邮件；已经领取后改变发放方式会被拒绝。
下一次扫荡必须重新调用 `is_customs`，不能用上一次的 `finish` 请求发起新收费。
协议没有会话请求键，因此跨新会话的延迟旧请求仍存在前述去重边界。

已完成但未领取的奖励不会随地图有效期过期，不允许离开接口删除或新开副本覆盖。
正常保存重启后，可重试对应 `finish` 和 `award` 完成领取；如果客户端在此阶段中断，
尤其是扫荡后中断，应重试原 `finish_type`，不能改成普通通关类型。
未实现客户端新增的“待领取奖励”恢复页面。通关接口校验已付费会话，不验证战斗录像或
客户端未上传的地图达成条件，属于本地 Mock 而非正式服防作弊系统。

## 范围与验证

客户端续玩接口只请求重建 `map_id` 对应地图，未发现上传房间、NPC 内存状态的续玩契约；
本实现恢复的是已付费副本会话，不保证恢复到断线前的房间和战斗现场。

运行专项测试：

```powershell
python -B -m unittest test_challenge_entry test_challenge_lifecycle test_challenge_rewards -v
```

覆盖加密 HTTP 调用、真实配置扣费、并发重复确认、门票校验与堆叠、账户隔离、
保存重启续玩、过期离开、离线恢复、恢复边界、时钟回拨和活动次数限制；另覆盖全部奖励
分支配置、普通/扫荡奖励差异、邮件发放、资源上限、重复结算、待领奖重启恢复及伪造奖励输入。
